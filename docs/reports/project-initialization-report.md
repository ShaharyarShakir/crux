## 1. Summary of Implementation

Milestone 17 establishes the foundational project conventions and initialization subsystem for Crux v0.2.0. Crux operates under the **Crux-Managed CMake (Option A)** architectural boundary: Crux is the user-facing project and build manager, and CMake is an internal build backend. Ordinary Crux projects are configured via `crux.toml`, discover sources according to standardized conventions, and do **not** require or generate a root-level `CMakeLists.txt`.

Key capabilities delivered in M17:
- **Multi-Language Project Initialization**: Scaffolds standardized C, C++, and Other project structures.
- **Compilable Starter Applications**:
  - **C**: Generates `src/main.c`, `src/modules/calculator.c`, and public header `include/<name>/calculator.h` with header guards and standard C17 defaults.
  - **C++**: Generates `src/main.cpp`, `src/modules/calculator.cpp`, and public header `include/<name>/calculator.hpp` inside project namespaces with standard C++20 defaults.
  - **Other**: Generates standard Crux directory trees without C/C++ compiler assumptions or starter code.
- **Interactive & Non-Interactive CLI**:
  - Interactive menu when stdin is an interactive terminal (`std::io::stdin().is_terminal()`).
  - Piped input support for scripted automation (`echo 1 | crux init`).
  - Safe default fallback to C++ (`c++20`) in non-interactive environments without input.
  - Positional directory paths (`crux init <path>`), language flags (`-l`, `--language`), and standard flags (`-s`, `--standard`).
- **Deterministic Lockfile Initialization**: Generates canonical `crux.lock` version 1 alongside `crux.toml` upon initialization.
- **Strict Overwrite Safety**: Atomic file verification ensures Crux refuses to overwrite any existing manifests, lockfiles, or user source files.

## 2. Final Project Structure

Crux establishes the following canonical project directory convention:

| Directory / File | Purpose | Generated by Default |
|---|---|---|
| `crux.toml` | Project configuration, metadata, and dependencies | Yes |
| `crux.lock` | Resolved dependency versions and cryptographic digests | Yes |
| `src/` | Application source files | Yes |
| `src/modules/` | Source modules and internal implementations | Yes (C / C++) |
| `include/` | Public headers directory | Yes |
| `include/<project_name>/` | Public headers namespaced by sanitized project name | Yes (C / C++) |
| `tests/` | Project unit and integration tests | Yes |
| `.crux/` | Crux-managed internal cache, build, and integration data | Yes |
| `.crux/.gitkeep` | Git tracking placeholder for Crux data directory | Yes |
| `.crux/build/` | Build outputs | Future (M18/M19) |
| `.crux/build/generated/` | Internally generated CMake configuration (not in root) | Future (M19) |
| `.crux/installed/` | Project-installed dependency artifacts | Future |
| `.crux/cmake/` | Crux CMake integration files | Future |

## 3. Supported Initialization Modes

Crux supports flexible interactive and non-interactive initialization:

1. **Explicit Language Selection**:
   ```bash
   crux init my-app --language c
   crux init my-app --language cpp
   crux init my-app --language other
   ```
2. **Positional Target Directory**:
   ```bash
   crux init path/to/my-app -l cpp
   ```
3. **Interactive Menu**:
   When stdin is a terminal and `--language` is omitted:
   ```text
   Select project language:
     1) C
     2) C++ (default)
     3) Other
   Enter choice [1-3, default: 2]: 
   ```
4. **Piped Input**:
   ```bash
   echo 1 | crux init piped-c-project
   ```
5. **Language Standard Overrides**:
   ```bash
   crux init my-app --language c --standard c11
   crux init my-app --language cpp --standard c++17
   ```
6. **Mismatched Standard Rejection**:
   - Rejects C++ standards for C (`--language c --standard c++20`).
   - Rejects C standards for C++ (`--language cpp --standard c17`).
   - Rejects any standard for Other (`--language other --standard c17`).
   - Rejects unknown languages (`--language rust`).

## 4. Manifest Schema Changes

The manifest parser and domain model in `src/project/manifest.rs` was updated to support both modern Crux `[project]` manifests and legacy `[package]` manifests:

### New `[project]` Manifest Format
```toml
[project]
name = "my-app"
version = "0.1.0"
language = "cpp"
standard = "c++20"

[dependencies]
```

### Backward Compatibility Guarantees
- `Manifest::from_toml_str` accepts both `[project]` and `[package]`.
- Existing manifests with `[package]` continue to parse, validate, and serialize identically.
- Manifests defining both `[project]` and `[package]` sections simultaneously are rejected with a clear diagnostic.
- `ProjectLanguage` enum supports `C`, `Cpp` (with `c++` alias), and `Other`.
- Standard normalization automatically translates `cpp20` to `c++20` and lowercases C standards (`C17` to `c17`).

## 11. M17 Follow-up: Minimal Project Structure

Following community review, the default project structure generated by `crux init` was streamlined in accordance with the principle: **"Start small. Let projects grow naturally."**

### 11.1 New Canonical Default Structures

Crux initialization generates only the essential files required for a clean, compilable project:

#### C Project (`crux init demo --language c`)
```text
demo/
├── crux.toml
├── crux.lock
└── src/
    └── main.c
```
- Standalone `src/main.c` printing `"Hello from demo!"`.
- No example modules (`src/modules/` removed).
- No empty header include tree (`include/` removed).
- No empty test tree (`tests/` removed).
- No empty Crux metadata tree (`.crux/` removed).

#### C++ Project (`crux init demo --language cpp`)
```text
demo/
├── crux.toml
├── crux.lock
└── src/
    └── main.cpp
```
- Standalone `src/main.cpp` using `<iostream>` printing `"Hello from demo!"`.
- No example modules (`src/modules/` removed).
- No empty header include tree (`include/` removed).
- No empty test tree (`tests/` removed).
- No empty Crux metadata tree (`.crux/` removed).

#### Other Project (`crux init demo --language other`)
```text
demo/
├── crux.toml
├── crux.lock
└── src/
```
- Only creates `crux.toml`, `crux.lock`, and an empty `src/` directory.
- No starter source files and no language assumptions.

### 11.2 Optional Directories Policy
The following directories remain standard and recognized in Crux, but are user-created or created on demand:
- `src/modules/`: Created by users when modularizing internal code.
- `include/`: Created by users when exporting public library interfaces.
- `tests/`: Created by users when adding test suites.
- `.crux/`: Created automatically by Crux commands when internal artifacts or caches are produced.

### 11.3 Discovery Rule
Crux formally establishes the architectural rule:
> **Crux recursively discovers application source files under `src/` only.**
