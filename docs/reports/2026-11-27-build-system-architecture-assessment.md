# Crux Build-System Architecture Assessment (second pass)

**Date**: 2026-11-27
**Baseline**: `main` @ `cdda319` (v0.3.0)
**Scope**: Assessment only. No source, test, manifest, website or existing document was changed. No Git write operation was performed on this repository. (The reproductions needed a Crux registry, which must be a Git repository, so a throwaway one was initialised and committed in the scratch directory.) This file is the only addition to the repository.

An earlier untracked report, `2026-11-25-build-system-architecture-assessment.md`, covers the same question and was left untouched. This pass was done from the code first, then compared against it. Section 14 lists where the two differ.

Evidence labels used below:

- **[reproduced]**: observed by running `target/debug/crux` (v0.3.0, no source file newer than the binary) or a real tool in an isolated scratch directory.
- **[code]**: established by reading the cited code, not executed.
- **[unverified]**: inference or general knowledge. Confirm before relying on it.

`cargo test`, `clippy`, `fmt` and `check` were **not run**: there is no Rust toolchain outside the Nix shell, and the shell could not be built offline.

---

## 1. Summary

1. **Meson is feasible, and the application side needs almost no change.** Applications consume dependencies through the file inventory in `installed.toml`, not through CMake metadata.
2. **Fix four correctness gaps before adding a second backend.** All are reproduced, and a Meson adapter would inherit every one:
   - an application can link an **older installation** than the one just built;
   - an edited local dependency is not rebuilt by `crux run`;
   - the package fingerprint ignores `CC`, so two compilers share one cache entry;
   - a package cannot see its own Crux dependencies while it is being built.
3. **A new trait is not justified yet.** Use a closed `enum` and a shared pipeline in which adapters describe commands and core runs them. Revisit at a third adapter.
4. **The registry is the sharpest compatibility constraint.** One `package.toml` that v0.3.0 cannot parse fails loading of the *whole* registry. Adding a `meson_args` key to the official registry would break every existing client.
5. **No `crux.toml` or `crux.lock` change is needed.**

## 2. Current architecture and build lifecycle

Crux has **two separate CMake pipelines** that share little code.

| | Package pipeline (dependencies) | Application pipeline (your project) |
|---|---|---|
| Engine | `CMakeBuildEngine` (`src/build/engine.rs`), `CMakeInstallEngine` (`src/install/engine.rs`) | `AppBuildEngine` (`src/build/app.rs`), `generate_app_cmakelists` (`src/build/generator.rs`) |
| CMake input | upstream `CMakeLists.txt` | `CMakeLists.txt` generated by Crux |
| Compiler detection | `detect_toolchain` (`engine.rs:127`) | `detect_project_toolchain` (`build/toolchain.rs`) |
| Cache key | `BuildFingerprint::compute` | `app_build_fingerprint` |
| Layout | `.crux/builds/<name>/<ver>/<fp>/` | `.crux/build/<profile>/` |
| Process runner | `run_logged`, no timeout | `run_logged`, 10 min configure and 30 min build timeouts |

Only the package pipeline needs to become build-system-agnostic.

### 2.1 Commands

| Command | Path |
|---|---|
| `crux build <pkg>` | `run_package_build` (`cli/commands/build.rs:387`) → `require_supported_build_system` → `acquire_definition` → `build_configuration_for` → `report::build_package` → `CMakeBuildEngine::build`. Builds that one package only, no dependency closure, no install. |
| `crux build` (`[package]` or lockfile only) | `run_lockfile_dependencies_build`: `sort_packages_topologically`, then the same engine per package. |
| `crux build` (`[project]`) | `run_app_build` → `ensure_app_dependencies` → (`run_lock`, `run_install` as needed) → `AppBuildEngine::prepare` → `execute_with_tee`. Default profile: debug. |
| `crux install [pkg]` | `run_install` (`cli/commands/install.rs`): per package, `CMakeBuildEngine::build` then `CMakeInstallEngine::install`. Default profile: release **[reproduced]**. |
| `crux run` | Same as an application build, then executes the binary with the runtime library path set. Ad-hoc mode goes through `prepare_adhoc_build` (`build/adhoc.rs`), which calls `detect_cmake` directly. |
| `crux integrate cmake` | `generate_cmake_dependencies` (`integrate/cmake.rs`). Consumer-side only. |

### 2.2 Package lifecycle and caching

1. **Definition**: `ActiveCatalog::definition` (`source/direct.rs`).
2. **Gate**: `require_supported_build_system` (`cli/commands/mod.rs`) rejects any `build.system` other than `cmake`. A missing `[build]` is treated as CMake.
3. **Acquire**: `acquire_definition` or `acquire_locked_with_status` → `source_dir` + `checksum`.
4. **Probe**: `cmake --version`, Ninja if present else `Unix Makefiles`, first line of `gcc --version` and `g++ --version` unless overridden.
5. **Fingerprint**: `BuildFingerprint::compute` (`build/fingerprint.rs:38`).
6. **Build cache**: `cached_result` reuses a build when `metadata.toml` matches and every recorded artifact still has its size. It requires at least one artifact.
7. **Configure**: `cmake -S -B -DCMAKE_BUILD_TYPE -G [-DBUILD_SHARED_LIBS] [-DCMAKE_*_COMPILER] <cmake_args>`.
8. **Compile**: `cmake --build <dir> --config <type> [--parallel N]`.
9. **Artifacts**: `scan_artifacts`, skipping CMake and Ninja internals; write `BuildMetadata`.
10. **Install cache**: `check_existing_cache` on `.crux/installed/<name>/<ver>/<fp>/`.
11. **Install**: `cmake --install` into a staging directory, using `DESTDIR` plus `promote_unwrapped_prefix` when `cmake_install.cmake` mentions absolute destinations.
12. **Publish**: `scan_staging_dir` → `installed.toml` → atomic rename.
13. **Consume**: `validate_package_installation` → `plan_app_dependencies` → include directories and library paths written into the generated application project.

### 2.3 CMake execution boundaries

| What | Where |
|---|---|
| Probe | `engine.rs:127` `detect_toolchain`; `app.rs:735` `detect_cmake`; `app.rs:786` `select_generator` |
| Package configure and compile | `engine.rs`, `BuildEngine::build` (from line 407) |
| Package install | `install/engine.rs`, `InstallEngine::install` (from line 225); uses `cmd.output()`, so no timeout, no live output, and `extra_env` is not applied |
| Application configure and compile | `app.rs`, `execute_with_tee` |
| Reading CMake files | `validate_build_result`, `has_absolute_dest` (`install/engine.rs`); `build_dir_is_stale` (`app.rs:862`) |

The sanitizer, standard-support and compiler probes invoke the compiler directly, not CMake.

## 3. Correctness gaps found

These exist in v0.3.0 independently of Meson.

### 3.1 The application can link a stale installation **[reproduced]**

`validate_package_installation` (`integrate/validation.rs:26`) sorts the fingerprint directories (line 71) and takes the **first** valid one for the profile (line 267). The fingerprint is a hash, so the order says nothing about which is current.

A local path dependency was edited six times, running `crux lock`, `crux install --profile debug`, `crux run` each time:

| Source returns | App printed |
|---|---|
| 100 | 100 |
| 101 | **100** |
| 102 | **100** |
| 103 | **100** |
| 104 | 104 (its hash happened to sort first) |
| 105 | **104** |

The same mechanism applies to a compiler or CMake upgrade, or a `cmake_args` change: any case where a second fingerprint directory appears **[code]**.

**Direction**: the installer should record which fingerprint is current per `(name, version, profile)` (for example a small `current-<profile>` file in the version directory, written atomically; the existing scan only looks at directories). Validation should follow that record, and should fail rather than guess when there is no record and several candidates.

### 3.2 Edited dependencies are not rebuilt automatically **[reproduced]**

`ensure_app_dependencies` calls `run_install` only when validation *fails* (`cli/commands/build.rs:311`). After editing a path dependency, `crux run`, and then `crux lock` followed by `crux run`, both still ran the old code. Whether `build`/`run` should do this for mutable path sources is a design decision; it should at least be documented. Recipe, toolchain and Crux changes are missed the same way **[code]**.

### 3.3 The package fingerprint can describe the wrong compiler **[reproduced]**

`detect_toolchain` falls back to the literal `gcc`/`g++` (`engine.rs:175`, `184`) and ignores `CC`/`CXX`. No compiler flag is passed to CMake unless configured, so CMake honours `CC`.

- With `CC=clang`, `crux build leaf` reported **reused cached build** for the gcc-built entry.
- In a fresh project, `CC=clang` compiled with clang (`CMakeCache.txt`) while `metadata.toml` recorded `c_compiler_version = "gcc (GCC) 15.3.0"`, under the same fingerprint as the gcc build.

`CFLAGS`, `CXXFLAGS` and `LDFLAGS` are likewise read by CMake and not hashed **[code]**. The application pipeline does honour `CC`/`CXX`, so a project can compile its own code and its dependencies with different compilers.

### 3.4 Packages cannot see their Crux dependencies **[reproduced]**

`BuildRequest` has no dependency field, and nothing sets `CMAKE_PREFIX_PATH`, `CMAKE_MODULE_PATH` or `PKG_CONFIG_PATH` for package builds. With `mid` depending on `leaf`, `crux lock` succeeded and `leaf` installed, then `mid` failed with `Could not find LEAF_LIB`.

`BuildFingerprint::compute` also has no dependency input, so a changed dependency would not invalidate its dependents **[code]**. No definition in `registry/packages/` declares a dependency today, so the official registry does not hit this. Direct sources with dependencies do. A package may also silently pick up a system copy of a library instead of the locked one **[unverified]**.

### 3.5 Smaller items

- **Header-only packages with no build outputs never hit the build cache** **[reproduced]**: `!metadata.artifacts.is_empty()` (`engine.rs:236`). Two consecutive builds both recompiled. A Meson header-only package would do the same.
- **`promote_unwrapped_prefix` can drop files** **[code]**: if `usr/local` exists it hoists that and then removes all of `usr/`, including anything installed under `usr/` outside `local/`.
- **Adjacent, security-relevant** **[code]**: `crux install <pkg>` (`cli/commands/install.rs:234`) and `crux build <pkg>` (`build.rs:469`) use `acquire_definition`, so the checksum in `crux.lock` is not checked, even with `install --locked`. Out of scope here; worth a separate look.

## 4. Core versus CMake-specific responsibilities

| Belongs in Crux core | CMake-specific today |
|---|---|
| Identity, resolution, lockfile, registry, acquisition, checksums | `CMakeLists.txt` precondition, `BuildError::MissingCMakeLists` |
| Directory layout, cache lookup and validation (currently inside `CMakeBuildEngine`) | Configure, compile and install argument construction |
| Process execution, logs, `-vv` tee, failure tails (`core/process.rs`) | `cmake_args` (in `BuildConfiguration`, `BuildSection`, `build_configuration_for`) |
| Compiler detection and identity, sanitizer probe | `as_cmake_build_type`, `BUILD_SHARED_LIBS`, generator choice |
| Staging, inventory, traversal and symlink guards, atomic publication, `installed.toml` | `CMakeCache.txt` / `cmake_install.cmake` checks, absolute-destination detection |
| Link planning and installation validation | Artifact-scan ignore list |
| | `ToolchainInfo.cmake_version`, `CMake*` error text, wording in `cli/report.rs` |

`crux integrate cmake` is a third thing: **consumer** support, unrelated to how a dependency was built. The application backend (`generator.rs`) is a fourth: an internal choice that can stay CMake.

## 5. Adapter boundary and the trait question

### 5.1 Boundary

**The adapter says what to run and what to expect. Core runs it.** One adapter covers both build and install, since a system's install step depends on how it configured.

| Adapter supplies | Core does |
|---|---|
| Marker file, tools to probe | Probe execution, missing-tool diagnostics |
| Option validation, fingerprint fields | Hashing, cache layout and lookup |
| Configure, compile, install command specs | Spawning, environment scrubbing, timeouts, logs, tee |
| "Is this build dir configured" check | Staging, inventory, guards, publication |
| Artifact ignore rules | Metadata, link planning |

### 5.2 Is a trait justified?

`BuildEngine` and `InstallEngine` already exist, each with one implementor and no polymorphic use. `report::build_package` takes `&CMakeBuildEngine` and calls the inherent `is_fresh`. They wrap the whole pipeline, which is the wrong level: a `MesonBuildEngine` implementing them would copy caching, metadata and log handling.

| Alternative | Assessment |
|---|---|
| Second implementor of today's traits | Reject: duplicates the pipeline. |
| **Closed `enum BuildSystemKind { Cmake, Meson }`, one module per system, `match` in a shared pipeline** | **Recommended.** The set is in-tree and closed, `match` is exhaustive, no new public contract to keep stable. |
| Narrow step-level trait | Reasonable at a third adapter, or if the `match` arms grow beyond a few. Cheap to introduce from the enum modules. |
| Argv templates in `package.toml` | Reject for real build systems: they need probing and post-conditions. |
| External plugins | Reject: new trust boundary and ABI. |

So: **a Rust trait is not justified now.** Keep the existing public traits and types as they are for compatibility.

## 6. Proposed context and result contracts

Sketches only, not final signatures.

```rust
// core -> adapter
struct BuildContext<'a> {
    package_id: &'a PackageId,
    source_dir: &'a Path,
    build_dir: &'a Path,
    staging_dir: &'a Path,
    profile: BuildProfile,
    compilers: &'a ResolvedCompilers,     // resolved once, passed explicitly to the tool
    shared_libs: Option<bool>,
    jobs: Option<usize>,
    options: &'a [String],                // validated by the adapter, opaque to core
    env: &'a BTreeMap<String, String>,
    dependency_prefixes: &'a [PathBuf],   // missing today (3.4)
}

// adapter -> core
struct StepSpec { step: Step, program: PathBuf, args: Vec<OsString>, env: BTreeMap<OsString, OsString> }

// core -> caller
struct BuildOutcome {
    system: BuildSystemKind,
    tools: BTreeMap<String, String>,      // "cmake" / "meson" / "ninja" -> version
    fingerprint: BuildFingerprint,
    artifacts: Vec<BuildArtifact>,
    logs: StepLogs,                        // configure, build, install
    reused_cache: bool,
}
```

- The install result stays as `InstallResult`; nothing in it is CMake-specific.
- Errors: add generic variants carrying the tool name, and keep today's CMake wording, which tests assert on.
- `src/lib.rs` re-exports `BuildRequest`, `BuildResult`, `BuildConfiguration`, `ToolchainInfo`, both engines and both traits. Adding struct fields breaks external struct literals (`tests/build.rs` builds `ToolchainInfo` literally), so treat shape changes as public API changes.

## 7. Fingerprints and cache compatibility

### 7.1 Fields in `BuildFingerprint::compute`

| Field | Class |
|---|---|
| name, version, source digest, profile | Universal |
| C and C++ compiler version line and override path | Universal (content is weak: no target triple) |
| shared flag, sorted extra environment | Universal |
| `cmake_version`, `generator` | CMake-specific |
| sorted `cmake_args` | CMake-specific |
| Absent | system id, format version, target and host, dependency fingerprints, ambient compiler environment |

The encoding is not length-prefixed or versioned. The digest names both the build and install directories. No test pins a literal digest (`tests/build.rs` checks determinism and divergence only).

### 7.2 Rules for evolving it

1. **First add a golden-digest test** for fixed inputs.
2. **Keep the CMake preimage byte-identical for clean builds, and append new data only when it exists**:
   - dependency fingerprints only when the package has dependencies, so every current registry package keeps its digest;
   - `CFLAGS`, `CXXFLAGS`, `LDFLAGS` only when set.
3. **Compiler fix**: resolve override → `CC`/`CXX` → current `gcc`/`g++` default, hash what was resolved, and pass it explicitly to CMake. With `CC`/`CXX` unset the hashed strings do not change. Users with them set get new digests, which is correct. Two cautions: entries already poisoned under a gcc digest stay on disk (a forced rebuild or one deliberate format bump clears them), and hosts without `gcc` need today's behaviour as an explicit fallback.
4. **Meson gets its own labelled, versioned preimage**, in the style of `app_build_fingerprint` (`crux-pkg-meson-v1`): identity, source, profile, compiler identity including target triple, Meson version, linkage, options, environment, dependency fingerprints. It cannot collide with CMake entries by construction.
5. **Metadata**: add `system` and `tools` with `#[serde(default)]`; absent means CMake. `format_version` can stay 1.
6. Two fingerprint directories for one version are only safe once 3.1 is fixed. Forbidding a system change for a published `name@version` is good registry policy, but it does **not** fix 3.1, which needs no system change.

Sanitizers and `[build]` flags apply to applications only, so they stay out of package fingerprints.

## 8. Dependency installation and exposure

**Both systems can share the install contract**: a prefix tree plus `installed.toml`. `build/dependency.rs` derives everything from the inventory:

- headers → the nearest `include/` ancestor, else the install root;
- libraries → all static libraries if any exist, else all shared ones with runtime directories;
- no reading of `.cmake`, `.pc` or `CMakeCache.txt`.

Limits that apply to any build system **[code]**:

- A package whose headers must be included from `include/<subdir>/` as the search root will not compile, because that flag lives in its `.pc` or CMake config, which Crux does not read.
- Required system libraries and compile definitions are lost for the same reason.
- Several static libraries in one package are linked in alphabetical order, which may not satisfy their internal dependencies.

CMake assumptions to move into the adapter: the `CMakeCache.txt`/`cmake_install.cmake` precondition, `--prefix` at install time, the absolute-destination scan.

`crux integrate cmake` only sets CMake search paths. A Meson package that ships a `.pc` file and no CMake config may not be found by `find_package` in an external CMake consumer **[unverified]**.

## 9. Manifest and registry design

### 9.1 Today

- `package.toml`: `[build] system = "..."`, `cmake_args`, with `deny_unknown_fields` (`registry/metadata.rs:44`). `system` is a free string.
- The official registry has 53 definitions: 18 `cmake`, 35 `catalog-only`. `catalog-only` is a support marker, not a build system.
- No `[build]` means CMake.
- Direct sources use the same parser on their own `package.toml`.
- `crux.toml` `[build]` is application flags and sanitizers only.

### 9.2 Recommendation

- Keep `[build].system` as the only selector: `cmake` (default), `meson`, `catalog-only`. Parse it into a typed value internally; keep unknown strings loadable.
- Keep the missing-`[build]`-means-CMake default. Do not auto-detect from marker files.
- **No change to `crux.toml` or `crux.lock`.** The build system is a property of the package.
- When Meson options are needed, add `meson_args` beside `cmake_args` rather than a generic options table.

### 9.3 Registry compatibility **[code]**

`GitRegistry::open` parses every definition with `?` (`registry/git.rs:225`). One failure aborts the whole load.

| Registry change | Effect on v0.3.0 |
|---|---|
| `system = "meson"`, no new keys | Safe: loads; building that package is rejected with a clear message |
| Any new key such as `meson_args` | **Entire registry fails to load** |
| Bumping `format_version` | Entire registry refused (deliberately) |

Therefore:

1. The first Meson packages should need **no new keys**.
2. Ship a release that tolerates unknown `[build]` keys, or skips only the affected definition, *before* the official registry uses one. Older clients still break, so this also needs a published minimum version or a separate registry location.
3. Do not reuse `cmake_args` for Meson options to dodge the problem.

## 10. Meson feasibility

### 10.1 Lifecycle mapping

| Step | CMake | Meson |
|---|---|---|
| Marker | `CMakeLists.txt` | `meson.build` |
| Configure | `cmake -S src -B build ...` | `meson setup build src --backend=ninja --buildtype=debug\|release --prefix=/usr/local --libdir=lib --default-library=static --wrap-mode=nodownload -Dpkgconfig.relocatable=true <options>` |
| Compile | `cmake --build build` | `meson compile -C build -j N` |
| Install | `cmake --install build --prefix stage` | `meson install -C build --destdir stage --no-rebuild`, then `promote_unwrapped_prefix` |
| Compiler | `-DCMAKE_*_COMPILER` | `CC`/`CXX` environment at first setup, or a native file |

### 10.2 Probe results (Meson 1.10.2, Ninja 1.13.2, one tiny C library) **[reproduced]**

The probe ran `setup`, `compile` and `install --destdir` by hand, not through Crux.

| Observation | Consequence |
|---|---|
| Default `libdir` was `lib64` | Pass `--libdir=lib` |
| Default `default_library` was `shared` | CMake packages usually default to static; pass it explicitly or linkage differs by build system |
| Default prefix `/usr/local`; `.pc` baked it | `-Dpkgconfig.relocatable=true` with a relative libdir produced `prefix=${pcfiledir}/../..` |
| `meson-private/sanitycheckc.exe` is left executable in the build dir | The artifact scan must ignore `meson-private/` and `meson-info/` |
| `setup` on a configured directory exits 0 without reconfiguring | On force or after failure, wipe the directory or pass `--reconfigure`/`--wipe` |
| Compiler chosen was `cc` | Set `CC`/`CXX` explicitly and fingerprint the result |

Not probed: C++, subprojects, minimum supported versions, a real upstream package.

### 10.3 Tools, Ninja and Make

- Required: `meson` (which needs Python), `ninja`, a compiler. `pkg-config` only for packages that look up dependencies.
- **Ninja is an executor, not an adapter.** CMake selects it with `-G Ninja`; Meson uses it as its backend. It belongs in tool probing and the fingerprint's tool fields.
- **Make** is CMake's fallback generator and the likely Autotools executor. Meson has no Make backend.
- `flake.nix` provides neither `meson` nor `ninja`. This machine has both from the system profile, so tests that pass locally may not run in the dev shell or CI. Adding them is a build-environment decision, not a Rust dependency.

### 10.4 Other risks

- `--wrap-mode=nodownload` limits subproject downloads; it does not sandbox build scripts, which can run arbitrary commands.
- Meson dependency lookup needs `PKG_CONFIG_PATH` or `CMAKE_PREFIX_PATH` for Crux prefixes, and the system search path should be controlled (3.4).
- Dependency `.pc` files built by CMake may not be relocatable, which would affect a Meson package consuming them **[unverified]**.

**Verdict**: feasible. A single leaf library is a modest job. Meson packages *with dependencies*, which is where many Meson projects sit **[unverified]**, depend on 3.4.

## 11. Future adapters (requirements only)

- **Autotools**: release tarball with a generated `configure` (regenerating needs the autotools chain); out-of-tree where supported, otherwise a writable copy of the source, since the cache must stay immutable; `make`, `make install DESTDIR=`; strict environment control; libtool and `.pc` prefix handling.
- **Custom scripts**: argv lists rather than shell strings, explicit environment, script content in the fingerprint, same `installed.toml` output. Inventory guards check what is installed, not what a script does while running, so real isolation must be designed before this ships.

## 12. Compatibility risks and migration

| Risk | Mitigation |
|---|---|
| Refactor silently changes CMake digests, orphaning caches | Golden digest test first |
| Refactor changes CMake arguments | Record configure, build and install argv before and after |
| New registry key breaks old clients | Section 9.3 |
| Stricter installation validation rejects existing installs without a "current" record | Accept a single candidate; rebuild the record when ambiguous |
| Dependency prefixes change what CMake finds | Apply only to packages that declare dependencies |
| Public API break | Add rather than change; keep existing types and traits |
| Error wording changes | Keep CMake messages identical |
| Tool-dependent tests | Skip explicitly when tools are absent, and say so in output |

## 13. Recommended milestones

Correctness comes first because later work multiplies fingerprint directories.

| # | Milestone | Done when |
|---|---|---|
| **M0** | Characterisation: golden digest, argv recording, old-metadata parsing | Passes on unchanged code |
| **M1** | Current-installation selection (3.1) and a decision on rebuild-on-change (3.2) | The six-step scenario in 3.1 prints the current value each time |
| **M2** | Toolchain truth (3.3), header-only caching | `CC` change yields a new digest; clean-environment digests unchanged |
| **M3** | Dependency exposure and dependency fingerprints (3.4) | `mid` → `leaf` builds; changing `leaf` rebuilds `mid` |
| **M4** | Extract the shared pipeline; typed `BuildSystemKind`; CMake the only variant | M0 unchanged |
| **M5** | Meson adapter, local fixtures, then one dependency-free pilot package with no new registry keys | Builds, installs and links through `crux run` |
| **M6** | Registry tolerance, then `meson_args` | Compatibility documented and tested |
| Later | Autotools, custom | A concrete package needs it; separate assessment |

M1 to M3 are worth doing even if Meson is never added.

## 15. Non-goals

- Implementing anything in this assessment.
- Plugins; per-application choice of a dependency's build system; per-project dependency options.
- Replacing the CMake application backend.
- Ninja or Make as build-system variants.
- MSVC and Windows support, cross-compilation, binary caching.
- A pkg-config consumer integration.
- Sandbox design.

## 16. Unresolved decisions

1. Should `crux build`/`run` rebuild changed path dependencies automatically? Recompute fingerprints every run (slower, thorough) or compare recorded source checksums (cheaper, misses toolchain changes)?
2. How is the current installation recorded, and are old fingerprint directories ever pruned?
3. One deliberate CMake fingerprint format bump, or the append-only approach in 7.2?
4. How much ambient environment should package builds inherit?
5. Default linkage across build systems when the definition says nothing.
6. How packages declare system dependencies that Crux does not provide.
7. Registry compatibility policy for new keys (9.3).
8. Pilot package and minimum Meson and Ninja versions. Whether any `catalog-only` entry is a suitable Meson candidate was not checked against upstream sources.
9. Whether `meson.build` or `CMakeLists.txt` may sit in a subdirectory, which would need another recipe key.
